## $C551 の入口と呼出し経路

入口はbank $1Eの$C4A1。サブルーチン資料のブロック属性取得処理と実コードを照合した。
$C4A1から分岐を追うと$C504、$C543のJSR $D7A3、$C546のJSR $D758を経て、
$C54Eの `lda $B100,y`、$C551の `and #$F0` に達する。
$B100が属する切替バンクは不明な経路もあり、参照先のバンクまで確定したとは扱わない。

代表的な入口経路は次のとおり。

1. InitialThread $DDE8からゲームループへ進む。
2. $DEACのA=$1B、$DEAEのJSR $FF3DでR6=$1B・R7=$1Cを選択し、$DEB1で$8000を呼ぶ。
3. bank $1Bの$8000はRAM $30の状態番号を使い、$802Bで$8045の下位表、
   $8030で$8069の上位表を読み、$8035でJMP [$0000]する。
4. 表の先頭は$808Dを指し、$808DでJSR $8215、$8217でJSR $E7B7を呼ぶ。
5. $E7B7から呼ぶ$E814等の移動・衝突処理内で、$E81F等がJSR $C4A1を呼ぶ。

既存の原作用配置では奇数bank $1Bが既定の$A000になっており、$DEB1を解決できなかった。
さらに$FF43の要約はサウンド処理・再帰・間接ジャンプを含む全経路の効果を確定できず、
呼出し後のR6/R7を不明にしていた。配置だけを直しても、動的な$30の分岐表の全候補は分からない。
これらは実際のゲームの配置・呼出し規約・表の範囲が必要な箇所だった。

| 代表箇所 | 変更前 | 追加注釈後 |
|---|---|---|
| bank $1E $C551 | 周辺とまとめた `.db $29, $F0, ...` | `and #$F0` |
| bank $1E $DEB1 | 未解決の `jsr $8000` | `jsr sub_1B_8000` |
| bank $1B $808D / $8215 | 未到達のデータ | 表からの入口・JSR $E7B7を認識 |
| bank $1B $8045-$808C | 未分類のバイト | LOW/HIGH式のデータ表。命令にはしない |
| rock5g bank $1E $C551-$C552 | 既に `and #$FC` | 同じ2バイト命令を維持 |

## 汎用側の修正

- ルーチン要約は戻り時のA・X・Yを入力の記号値として保持する。
  全戻り経路の一致が必要で、不明な出口や食い違う値からは確定しない。
  これまで無条件に失っていた、値を返す処理やPHA/PLAによるレジスタ保存を扱える。
- 既知のX/Yによる添字付き読込み、既知のゼロページポインタと添字による読込みを扱う。
  ゼロページ・16ビットの折返しを守り、未知の索引・不明なPRGバンクから表の要素を選ばない。
- 要約処理でも、値が確定したポインタによる間接tail JMPをたどる。
  主追跡が既に扱えるジャンプを、要約だけが「不明な出口」にしていた差を解消した。
- サブエージェントのレビューで、スタックの普通のSTAによる上書きを見落とす指摘を受け修正した。
  JSR・pushが書くスタックRAMの旧値を破棄し、スタックページと内部RAMの鏡へ届きうる書込み、
  RAMへの効果が不明な呼出しでは抽象スタックの保存値も破棄する。
  例えばPHAした2をSTA $0100,Xで4に上書きした場合に、戻るAを2と確定しない。

5つの回帰テストを追加。通常の保存・既知の間接tail JMP・索引読込みの正例、
経路の合流・未知の索引やポインタ・スタック上書きの負例、オペランド1バイトの差分を
2バイトのAND命令全体に拡張するケースを検証した。元の不明な呼出し後にもスタックの
値が保たれるテストは、その前提が安全でないため負例と既知の呼出しの正例に分けた。
再レビューでは対応必須の指摘なし。

## ゲーム固有の追加注釈

既存の `Rockman5.disasm.json` は変更せず、`Rockman5.trace.disasm.json` に別保存した。
追加項目は次のJSON。他のラベル・領域・優先順位を保持した。
コード領域の線形指定は追加していない。

```json
{
  "banks": [{"bank": 27, "org": "$8000"}],
  "references": [{"bank": 30, "address": "$DEB1", "target_bank": 27}],
  "regions": [
    {"bank": 27, "start": "$8045", "length": 36, "type": "low_bytes", "pair": "$8069", "code_targets": true},
    {"bank": 27, "start": "$8069", "length": 36, "type": "high_bytes"}
  ]
}
```

$FF43は$FF4C/$FF5Aで$F5/$F6を読み、$FF50/$FF5EでMMC3 R6/R7へ書く。
サウンド処理末尾の$FFB1も$FF43へ戻って復元する。$FF22は$FF38でスレッドSPを保存し、
$FEE3-$FEF2でSPとX/Yを復元して再開する。$C147-$C168のNMI再開処理も照合した。
スケジューラによるバンク保持は断言できないため、原作の待機処理に `keeps_banks` は追加しない。
rock5gに既に存在する同指定はユーザーの注釈として保持している。
$FF43は$F3/$F4/$F2等のRAMも変更するため、その他RAMの保持を仮定する `switch_banks` の
指定を原作に追加せず、確認した呼出し$DEB1だけを `references` で解決した。
$8045/$8069の各36要素は、最初のハンドラ$808Dの直前までを占める。
この表の実バイトはrock5gと異なるため、原作の飛び先を改造版へ流用していない。
rock5gの現存注釈は変更していない。

## データの誤認と出力仕様の検証

追加表72バイトはLOW/HIGH式のデータとして出力され、既存のサウンド表・IRQ表もデータのまま。
原作資料の16ステージ分のマップ（各PRG bank 0-15、offset $0900-$094F）について、
命令として出力されていないことを生成ソースと照合した。パディングの `.ds` も維持。
原作の追加注釈後にinvalid_opcode、overlap、code_data_conflictはない。
これは全分類の正しさの証明ではなく、確認した範囲での検証である。

全workspaceテストにより、異なるバンクの合流、注釈優先順位、$DFFF/$E000をまたぐ命令、
生成チェックサム、手編集済みファイルの保護、バンク名の大文字16進表記を確認した。
実ROMでも字下げはタブ1個、エントリに `.catbank $1E` を確認。
差分版はベースPRGの `.incbin` 1個と末尾CHRの `.incbin` 1個で、CHR全262,144バイトが
対象ROMの元の順序と一致した。原作の全体版は既存仕様どおりCHRバンクファイルから読む。

両ケースで `mapper4_fixed_prg_16k=true`、MCPの
`disassemble → export_disassembly → check → assemble` を実行。
検査・アセンブルは診断0件、往復検証mismatch_count=0。
独立比較でもヘッダ込み524,304バイトが一致した。

`cargo fmt --all -- --check`、`cargo clippy --workspace --all-targets --locked -- -D warnings`、
`cargo test --workspace --locked` が成功。C# goldenは変更せず既存テストを通過。
アセンブラの出力仕様や公開JSON型に変更はない。

## 再現と残る課題

`tools/trace_rom.py` は標準ライブラリだけでMCPへ接続し、全ページの解析結果を回収する。
`--output` の拡張子を変えた `.nes` に再ビルドし、別パス・CHR・出力構成・全バイト・SHA-256を検査する。
ROMや生成物はコミットしない。プロジェクト内の注釈は別途必要。

```sh
cargo build --workspace --locked
python tools/trace_rom.py --server target/debug/nesasm-mcp.exe --root nesProjects/rock5g --annotations Rockman5.trace.disasm.json --output build/trace-new/Rockman5.asm
python tools/trace_rom.py --server target/debug/nesasm-mcp.exe --root nesProjects/rock5g --annotations rock5g.diff.disasm.json --output build/trace-new/rock5g.asm
```

Linux/macOSではサーバー名から `.exe` を外す。既存注釈との比較は原作のannotationsを
`Rockman5.disasm.json` に変え、別出力先を指定する。

原作bank $1B $9084は$9571/$9581の追加分離表を読むが、長さ・全状態の妥当性が未確認。
bank $1C $8036のオブジェクトディスパッチは$86C3のバンク表と$88C3/$8993のアドレス表を使い、
$805Bへの戻りアドレスを積む。無効オブジェクトIDや各バンクの配置を原作の実コードで
確認する必要があるため、rock5gの詳細表を原作へコピーしていない。
スレッドの間接入口や$C168の動的復帰先にも、スケジューラと実行時状態の情報が必要。
また、同じ物理バンクが複数CPU窓に配置される経路は、現在の単一org配置では解決できない。

rock5gの既存の$9F23 invalid_opcodeと$DF3E→$E4A6 overlapは基準時から存在する。
前者の入口が正しいか、後者が意図したスキップか誤った入口かを、改造版の独自コードで
確認する必要がある。[Issue #20](https://github.com/rock5easily/NesAsmRs/issues/20) に別記した。
バイト一致だけで正しいコード分類と判断していない。
