# Rust版の構成と検証

型の関係と処理の流れは [Rust版のUML図](rust-uml.md) を参照してください。

## 構成

Cargo workspaceは以下の3クレートで構成します。

| クレート | 役割 |
|---|---|
| nesasm-core | 2パスのアセンブラ、入力解決、画像変換、構造化結果 |
| nesasm-cli | 既存オプション、出力ファイル生成、watch |
| nesasm-mcp | rmcpによるstdio接続、6つのツールと入出力スキーマ |

`assemble(&AssembleRequest) -> AssembleResult` は標準出力、プロセスの作業ディレクトリ変更、
成果物の書き込みを行いません。要求ごとに新しい状態を使います。
`write_artifacts` が成功結果からROM、リスト、S-recordを書き込みます。
既存成果物の上書きには一時ファイルからのrenameを使い、入力ファイルの上書きを拒否します。
すべての一時ファイルを書き終えてからrenameを開始し、失敗時や巻き戻し時の
一時ファイルの後片付けは所有権と`Drop`で管理します。複数成果物のrename全体を
単一トランザクションとして扱うものではありません。

`build` はアセンブルと成果物の書き込みをまとめて行い、書き込みの失敗を `E_OUTPUT` 診断として
結果に加えます。CLIとMCPはどちらも `build` を使います。

アセンブラ本体は `engine/` に、行処理とシンボル（`mod.rs`）、疑似命令（`directive.rs`）、
命令（`instruction.rs`）、マクロ、条件アセンブル、プロシージャ、リスト、ROMイメージ（`rom.rs`）
のモジュールとして分けています。各行のディレクティブ・命令名は1回だけenumに分類します。
メモリ配置の定数は `state.rs` にまとめています。

内部のセクション、処理パス、ディレクティブ、命令名、include復帰イベントはenumで表します。
Rust APIの重大度・診断コード・データ種別・成果物種別・バンク・リストレベルも
`Severity`、`DiagnosticCode`、`DataType`、`ArtifactKind`、`BankRef`、`ListLevel` で表し、
JSONでは従来の `"error"`、`"E_IO"`、`"DB"`、`"rom"`、数値のバンク（定数は240）・
リストレベル（0〜3）を維持します。
MCP応答への変換は結果の所有権を移し、シンボル表などのコピーを避けます。
ソースの読み込みは上限付きで行い、読み込んだソースとPCXの変換結果は2つのパスで共有します。
`.INCBIN` はLayoutパスではサイズだけを使い、Emitパスで必要な範囲だけをseek/readします。
ROMイメージは書き込んだバンクまでだけ確保します。

`binary` はiNESヘッダを含まないROMペイロードで、C#の `ResultBinary` に対応します。
`header` が16バイトのiNESヘッダ（raw／S-record時は空）、`map` が既存のバンク配置情報です。
`-srec` はC#版と同様に `.nes` の代わりに `.s28` を出力します。
シンボルには名前・値・バンク・ページ・定義位置・公開属性・データサイズを含めます。
診断にはコード、重大度、ファイルと行、include／マクロの呼び出し元を含めます。
字句位置を特定していないため、現状の `column` はnullです。

## 互換性と意図した差分

既存NESASM構文、6502命令、C#拡張、マクロ・式・プロシージャ再配置、PCX/CHR、
iNES/raw/S-record、リスト出力、watchを提供します。PCE専用機能は対象外です。

- 既定文字コードは全OSでUTF-8です。SJISはWindows-932互換として明示指定します。
- パス区切りは各OSに従います。CLIの `NES_INCLUDE` は全OSで`;`区切りで、Windows以外では
  `:` も区切りとして受け付けます。先頭10個まで使い、超えた場合は警告を出します。
  入力探索は作業ディレクトリ、その後にincludeパスを使います。
- C#の未使用ROM・mapのゼロ初期値を維持します。MCPのバンク使用量は別途記録した
  書き込み位置から集計するため、未使用mapの値に依存しません。
- C#版の不具合は再現せず、Rust版では本来の動作とします。
  - `.DEFCHR` は8個の引数をタイルの8行として扱います。各引数は8ピクセル分の16進数で、
    最上位の桁が左端のピクセルです。0〜3以外のピクセル値はエラーです。
    C#版は引数をlittle-endianバイト列に変換した先頭8バイトを各行に使うため、
    `$11111111` が `$01` 相当になります。
  - マクロの `\#` は、空でない最後の引数の番号（引数がなければ0）を返します。
    C#版は9番目の引数が空だと常に9を返します。
  - `CATBANK` で次のバンクへ続いたデータも `_nb_bank` に数えます。C#版は数えません。
  - DB文字列の非ASCII文字は、ソースの文字コードのバイト列で出力します（UTF-8の `あ` は
    `E3 81 82`、`-e SJIS` では `82 A0`）。C#版は文字コードの下位1バイトだけを出力します。
  - 2番目以降の文字列引数に含まれる `\"` を正しく扱います。C#版はエラーまたは例外になります。
  - これらは比較ハーネスの既知の差分（`KNOWN_DIFFERENCES`）として扱い、Rustのテストで検証します。

### Rust版の拡張仕様

以下はC#版では受け付けない、またはC#版と挙動が異なる構文で、Rust版の仕様として提供します。

- `.DS count, fill` で領域を `fill` の値で埋めます。省略時は0です。
- 行末の `\`（コメントを除いた末尾）で次の行に継続します。継続行は空白1つで連結します。
  ファイル末尾で継続が終わらない場合はエラーです。
- 式で単項 `<`（下位バイト）と `>`（上位バイト）を使えます。即値（`#<value`、`#>value`）でも
  使えます。それ以外の命令オペランド先頭の `<`／`>` は従来どおりゼロページ／絶対アドレスの指定です。
- `lda.l`／`lda.h` は `low_byte`／`high_byte` と同じ意味です（C#版にはありません）。
- 式で `==` を `=` と同じ等値比較として使えます。
- `X`、`Y`、`A` をシンボル名として定義・参照できます。命令オペランドで単独の
  `A` は従来どおりアキュムレータ指定です。
- マクロ名は大文字小文字を区別しません。`foo` と `FOO` は同じマクロで、二重定義はエラーです。
- ネスト上限はC#版より緩く、マクロ展開とincludeを合わせて32段、条件アセンブルは64段です。
  1回のアセンブルで処理する行数は100万行までです。
- C#版の固定長バッファによる制限はありません。C#版は1行を158文字、文字列を127文字、
  マクロ・関数の引数を80文字で打ち切ります。
- 式は1つあたり256トークンまでで、式関数（`.FUNC`）の中から関数を呼ぶ深さは32段までです
  （C#版は値・演算子のスタックがそれぞれ64）。超えた場合は致命的エラーです。
- `-e SJIS` のとき、DB文字列にSJISで表せない文字があるとエラーにします。
- CLIの入力ファイルは1つだけで、`--json` と `-watch` は同時に指定できません。
- その他の上限（ROM 1 MiB、名前の長さ、iNESヘッダの値、アドレス範囲、プロシージャとCALL）は
  C#版と同じです。一覧は [ディレクティブのリファレンス](reference/directives.md#limits) を参照してください。
- C#版はPCXの初回ロードと名前付きBANKで未初期化文字列を参照して例外になります。
  Rust版ではPCXを正常に読み込み、BANK名を保存・検証します。
  この2つの例外を発生させる動作は再現しません。PCXはRustの独立したテストで検証します。
- エラーは結果として返し、MCPサーバのプロセスを終了しません。展開深度、式の複雑さ、
  ソースサイズ、ROM範囲の制限を超えた場合も診断を返します。
  式関数（`.FUNC`）の呼び出しは1回のアセンブルで合計100万回まで、`.INCCHR` の
  PCXファイルは約6MiBまでです。
- 前方参照により `.IF` の条件がパス1とパス2で変わる場合はエラーにします
  （C#版は警告のみで、パスごとに異なるコードを生成し得ます）。
  CLIの `--compat-if`、公開API／MCPの `options.compat_if: true` でC#版と同様に
  各パスの条件で処理を続行できます（既定は `false`）。パス1の未定義ラベルには
  `W_UNDEFINED_IF` 警告を返し、`-wd`／`warning_disabled` で抑制できます。
  このモードでは `.IF` 内の未定義ラベルの値は0、属性はBANK=240、PAGE／VRAM／PAL=-1、
  SIZEOF=0として評価します。パス2でも未定義のシンボルや、ラベル位置・バンクの不一致は
  引き続きエラーです。`.IFDEF`／`.IFNDEF` の動作は変えません。
- watchはH/R/Q + Enterでヘルプ、手動再生成、終了を操作し、標準入力の終端でも終了します。依存ファイル変更は
  自動検知します。MCPではwatchを起動せず、各要求時にファイルを読み込みます。
- エラー処理はC#版に合わせ、行単位のエラーは報告してパスを続行します。上限超過、
  バンク／ROM範囲あふれ、include失敗などの致命的エラーではそのパスを中断します。
  パス2でエラーになった行は、パス1と同じバイト数だけ位置を進めるため、後続行に
  位相エラーが連鎖しません。CLIの終了コードはエラー件数（1〜255に丸める）で、
  引数の誤りは2です。診断のパスはWindowsでも `\\?\` 接頭辞なしで表示し、
  閉じていない `.IF`／`.PROC` は開始行の位置で報告します。
- 次の点はC#版と意図的に異なります。
  - 診断は標準エラー出力に `ファイル:行: error [コード]: メッセージ` 形式で出力します。
    C#版の `pass 1`／`pass 2` 表示は出さず、成功時に `Assembled N bytes` を出します。
  - 失敗時は成果物（ROM・途中までのリスト）を書き込みません。
  - `-?` はオプションのリファレンスを表示します。
  - `.lst`／`.s28` の改行はOSの既定（WindowsではCRLF）です。JSONの `listing` はLFです。
- リージョン情報と `-s`／`-S` のセグメント使用量はC#版と同じ書式で表示します。
  JSON結果の `banks` にはバンク名とセクションごとの範囲、`ram` にZP／BSSの使用量を含めます。
- シンボルの `page` は、定数（EQU／RS）では `null` です。`PAGE()` はC#版と同じく
  -1（`$FFFFFFFF`）を返します。

ローカルMCPは `--root` を必須とし、正規化した依存ファイルと出力パスをこの範囲に制限します。
includeパスは各要求の `include_paths` で渡します。サーバは `NES_INCLUDE` を暗黙に使いません。
stdoutにはMCP通信だけを出力します。JSONとして解析できない行にはJSON-RPCの
`-32700 Parse error` を返します。サーバ名は `nesasm-mcp` として通知します。ROMバイト列は応答に含めず、成果物パスを返します。
`check` は同じ処理を実行して結果だけを返します。
リファレンス文書は `get_reference` ツールに加えて、resources（`nesasm://reference/<topic>`、
`text/markdown`）としても公開します。`resources/list` で6つのトピックの一覧、
`resources/read` で本文を返します。未知のURIは `-32002`（resource not found）です。
promptsとresource templatesは提供しません。

`check`／`assemble` の `sources` はルートからの相対パスをキーにしたソース文字列で、
`AssembleRequest.files`（メモリ上のファイル）としてディスクより優先して使います。INCLUDE・INCBIN・
INCCHRも同じ規則で探し、ルート外のパスは拒否します。メモリ上のファイルは書き込みません。
`lines` を指定すると `AssembleRequest.collect_lines` で各行の記録（`LineRecord`：位置、マクロの
呼び出し元、バンク、CPUアドレス、出力バイト（大きいデータは先頭64バイト）、サイズ、ソース行）を集め、
ファイル・行範囲・バンク・アドレス範囲で絞り込んだうえで既定200件（最大2000件）ずつ返します。

`inspect_rom` は `nesasm_core::inspect` を使い、ルート内のROMファイル（8 MiBまで）または
メモリ上でアセンブルしたプロジェクトについて、iNESヘッダ、$FFFAを含むバンクのベクタ、
警告（ヘッダとデータのサイズ不一致、ベクタがない、RESETがPRG ROM外）を返します。
`hexdump`（最大4096バイト）と `disassemble`（最大512命令）はバンクとCPUアドレスで範囲を指定します。
逆アセンブルはNESASM構文（ゼロページは `<`、間接は `[...]`）で、プロジェクトから作った場合は
ラベルとオペランドのシンボル名を付け、65C02専用の形式には印を付けます。

MCPの `assemble` が書き込めるのは、拡張子が `.nes` か `.bin` のROMと、その名前から
派生する `.lst`／`.s28` だけです。`.` で始まるファイルやディレクトリ（`.git` など）を
含むパスには書き込みません。CLIの出力先には、これらの制限を適用しません。

## 逆アセンブラ

ハンドアセンブルなどで作られたROMを、再利用できるNESASMソースに戻します。
`nesasm_core::disasm` が解析・ソース生成・往復検証を行い、MCPの `disassemble`／
`export_disassembly` から使います。CLIには提供しません。使い方と注釈の全項目は
[逆アセンブラのリファレンス](reference/disassembler.md) を参照してください。

- 入力は注釈（`DisasmConfig`、JSON）とROMです。注釈の `rom` がROMファイルを指し、
  ラベル・シンボル・領域（コード、バイト、ワード、ポインタ表、下位／上位バイト表、テキスト）・
  コメント・オペランドの上書き・参照先バンクを記録します。AIが作者のメモや仕様と
  逆アセンブル結果を突合し、その解釈を注釈に蓄積して再実行する使い方を想定しています。
  アドレスは数値または `"$C000"` 形式の文字列で書けます。
- `.nes` はヘッダのPRG数でPRG／CHRバンクを分けます。`.bin` は8 KiB単位のバンク列、
  `load_address` を指定すると任意アドレスに置く断片として扱います。PRGバンクのCPUアドレスは
  最後の2バンクが $C000／$E000、それ以外が $8000／$A000 の交互（1バンクなら $E000）を既定とし、
  `banks` で変更します。
- コードは割り込みベクタ・エントリポイント・コード領域・ジャンプ表から再帰的に追跡します。
  JSR・JMP・分岐の先をたどり、RTS・RTI・BRK・JMPで止まります。未定義のオペコードと
  65C02専用の形式はデータとして扱います。`inline_bytes`（JSR直後のインライン引数）と
  `no_return` も扱います。
- 自動ラベルは `sub_XXXX`（JSR先）、`L_XXXX`（分岐・ジャンプ先）、`D_XXXX`（データ）、
  ベクタは `NMI`／`RESET`／`IRQ` です。複数のバンクが同じアドレスを持つ場合はバンク番号を含めます。
  命令の途中への参照（BITによるスキップなど）は `label+n` と書きます。
- 生成するソースは元のROMとバイト単位で一致するように書きます。ゼロページは `<`、絶対アドレスは
  4桁（`lda $0012`）で、AUTOZPを使いません。$FFFFをまたぐ分岐は `*+n` と書きます。
  同じ値が16バイト以上続く範囲は `.ds n`（0以外は `.ds n, fill`、Rust版の拡張）にします。
  CHRバンクは `.incbin "<stem>.chr", offset, size`（既定）または `.db` です。
  `.include`／`.incbin` のパスはプロジェクトルートからの相対パスです。
- 生成ソースが512 KiBを超える場合（`options.split_banks` で指定も可）、バンクごとに
  `<stem>_bankNN.asm` に分け、メインファイルから `.include` します（ソースファイルは1 MiBまでのため）。
- `Disassembly::verify` は生成したソースとCHRファイルをメモリ上のファイルとしてアセンブルし、
  ヘッダとペイロードを元のROMと比較します（`.bin` は `raw`、断片は範囲外が0であることを確認）。
  差分は先頭20件をバンク・アドレス・期待値・実際の値・生成ソースの行で返します。
  NES 2.0のヘッダ（バイト7の下位4ビットや8〜15）とトレーナーはNESASMで再現できないため、
  課題（`header`）として報告し、検証は失敗します（トレーナーの512バイトも比較対象に含めます）。
- 課題（`issues`）は `header`、`invalid_opcode`、`overlap`、`code_data_conflict`、`indirect_jump`、
  `unresolved_bank`、`outside_rom`、`flow_leaves_rom`、`mapper_write`、`unknown_range` で、
  それぞれ注釈での解決方法を含むメッセージを返します。
- ROM Hackでは、注釈の `base` にベースROMを指定します。ベースと異なるバイトを（4バイト未満の間隔なら
  まとめて）範囲にし、命令とワード／ポインタ表の要素の境界まで広げ、注釈の `patches` の範囲を加えます。
  その範囲だけをソースにし、残りはベースROMから `.incbin "base.nes", offset, size` で取り込みます。
  コードの追跡はHack後のROM全体で行い、ソースが参照する未変更範囲のラベルは `name = $XXXX` で定義します。
  課題は変更範囲内のもの（とヘッダ）に絞ります。PRGバンクはベースのPRGバンクと、CHRバンクはCHRバンクと
  順に対応させるため、PRGを拡張したROMでもCHRがずれません。ベースにないバンクは全体をソースにし、
  変更のあるCHRバンクはバンク単位で出力します。ベースは同じ形式（`.nes`、またはバンク単位の `.bin`）で
  トレーナーのないものに限り、断片には指定できません。
  `Disassembly::diffs`（MCPの `diffs`、既定20件）は範囲ごとに、変更バイト数、コード／データ／未分類の
  バイト数、ベース側が同じ値の連続（空き領域）だったか、ラベル、ルーチン、範囲外からの参照
  （フックしたJSR・JMPなど）、先頭のバイト列を返し、AIがソースにする範囲を判断する材料にします。
- 注釈の誤り（不正な名前、名前の重複、範囲の重なり、存在しないバンクなど）は
  `E_DISASM`（`DiagnosticCode::Disasm`）の診断としてまとめて返します。

MCPの `disassemble` は書き込みを行わず、要約・課題（既定20件）・往復検証の結果と、要求に応じて
アドレス範囲のソース行（バイト列付き、既定200行・最大2000行）、名前またはアドレスへの相互参照、
ルーチン（呼び出し元の数、呼び出し先、読み書きするRAM）、RAMごとの読み書き回数を返します。
注釈ファイル・ベースROMと出力パスはルート内に限り、ROMとベースROMは8 MiBまでです。
`export_disassembly` は往復検証が一致した場合だけ `write_disassembly` で書き込みます。
書き込めるのは `.asm`（メインとバンクファイル）と同じ名前の `.chr` だけで、隠しパスとROM自体には
書き込みません。生成ファイルの先頭行には本文のチェックサム（FNV-1a）を記録し、既存ファイルは
チェックサムが一致する（生成後に編集されていない）生成ファイルの場合だけ上書きします。
メインの `.asm` には `.chr` のチェックサムも記録し、`.chr` はメインが上書きでき、かつ `.chr` 自体も
変更されていない場合だけ上書きします。リンクをたどった先の拡張子も確認し、`.asm`／`.chr` 以外
（ROMなど）には書き込みません。UTF-8として読めない既存ファイルも上書きしません。
`.include`／`.incbin` に書くパス（出力先と `base`）には引用符・制御文字、Windows以外では
バックスラッシュを使えず、ROMのパスはコメントで1行にまとめます。時間制限を過ぎた
`export_disassembly` は書き込みを行いません。注釈の値は範囲（1バンク内、`inline_bytes` は
8192まで、シンボルは $FFFF まで）を検証し、入力でpanicしないようにします。

1回のアセンブルには時間制限があります（既定30秒、`--timeout <秒>` で変更）。
超過するとエンジンを次の行で停止し、`E_TIMEOUT` の診断を返します。
ライブラリからは `assemble_with_cancel` にフラグを渡して同様に中断でき、
中断時は `E_CANCELLED` の診断を返します。

## ビルドとテスト

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo build --workspace --release --locked
```

CIはWindows x64、Linux x64、macOS ARM64、macOS Intelでclippy・テスト・リリースビルドを実施し、
`cargo fmt` の確認は1つのジョブで行います。テストにはgolden.jsonとの互換性比較と、
Windowsではジャンクション経由のルート脱出の拒否を含みます。
成功したバイナリをOS別のActions artifactとして保存します。
ワークフローは `main` へのpush、PR、手動実行に対応します。
公開先へのアップロードは行いません。ActionsはコミットSHAで固定し、
Rustツールチェーンは `rust-toolchain.toml` だけで指定します。

WindowsでC#との比較を実行するには.NET SDK（またはVisual StudioのRoslyn `csc`）とPythonが必要です。
比較ハーネスは.NET Framework 4.8を対象に、元のAssemblerソースを変更せずリンクして
ビルドします。参照アセンブリはNuGetから取得するため、古い4.5.2開発環境は不要です。

```powershell
# C#版（NesAsmSharp）のチェックアウト先を CSharpRoot で指定します
dotnet build tools/compat/Oracle.csproj --configuration Release -p:CSharpRoot=<NesAsmSharpのパス>
cargo build --workspace --locked
python tools/compat/compare.py --oracle tools/compat/bin/Release/net48/NesAsmOracle.exe --rust target/debug/nesasm.exe
# C#の結果を記録し直す場合
python tools/compat/compare.py ... --write-golden tools/compat/golden.json
```

各fixtureを別プロセスで実行し、成功・失敗、ROM全バイト、配置map、ヘッダ、
シンボル（両方向に名前と値・バンク・データサイズ）、領域サイズ、S-record、リストを比較します。
さらにRustが書き出した `.nes`／`.s28`／`.lst` ファイルを、改行コードと文字コードを含めて
バイト単位で比較します。失敗するケースではエラーの行番号を比較し、終了コードがエラー件数で
あることも確認します。診断文言は完全一致を求めません。
Rustが意図的に異なる動作をするケースは `KNOWN_DIFFERENCES`（シンボル単位は
`KNOWN_SYMBOL_DIFFERENCES`）に理由とともに列挙し、FAILではなくKNOWNとして報告します。
比較結果は `target/compat/cases` に保存し、CI失敗時にはartifactとして回収します。

`--write-golden tools/compat/golden.json` で、一致したケースのC#の結果を記録します。
`cargo test` の `golden` テストがこのファイルと比較するため、C#を実行できない
Linux・macOSでも同じ互換性ケースを検証できます。CIの互換性ジョブは、記録済みの
golden.jsonが最新のC#の結果と一致することも確認します。

既存fixtureに加え、全命令・アドレッシング形式、式、マクロ引数、前方参照、
プロシージャ・グループ、バンク境界と復帰、リストのレベル、文字コードを検証します。
Rustの統合テストはMCPの実際のstdio通信、失敗後の復帰、成果物生成、watch、
入力・出力パス制限、PCX変換と不正画像も対象とします。逆アセンブラは、比較用fixtureから
作ったROMと乱数のROM・断片がすべて元のROMに再アセンブルできることを検証します。
